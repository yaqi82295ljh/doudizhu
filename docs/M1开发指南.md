# M1 规则引擎开发指南

> 配套文档：`立项书.md`（范围与决策）、`牌型规则.md`（阶段 3 前必须写）
> 本文不提供代码，只给"想什么、写什么、怎么验证"。代码由你自己敲。

---

## 0. 为什么先做引擎，而不是先做界面

大多数人做游戏项目的顺序是：先搭页面 → 再写逻辑 → 最后发现逻辑错了，页面全废。

正确顺序相反。判断依据很简单：**界面只是把状态画出来**。状态本身错了，画得再好看也是错的。而状态是否正确的唯一裁判，是规则引擎。

所以 M1 的目标不是"能玩"，而是：

> 给任何一手牌、任何一个上家出牌，引擎都能准确回答：这手牌是什么牌型？能不能出？有哪些更优选择？

这件事做完，后面 M2 的界面、M3 的联网、M4 的 AI 都是**在正确的地基上铺东西**。这件事没做完就往下走，后面每一步都在还债。

**判断自己有没有做完 M1 的标准**：随便报一手牌，你不用跑程序就能说出它是什么牌型、比谁大。做不到就还没懂。

## 1. 工作方法：红 → 绿 → 重构

你没写过单元测试，先接受一个反直觉的规矩：**先写测试，再写实现**。

```
1. 写一个测试，描述"我期望这个方法做什么"
2. 运行 → 红色（编译不过或断言失败）—— 正常，因为实现还没写
3. 写最少的代码让它变绿
4. 再写下一个测试
```

为什么顺序不能反？因为**先写实现时，你会不自觉地让测试去迁就实现**。比如你写顺子判断时漏了"不能含 2"，然后测试也照着漏掉的地方写，测试全绿，bug 留着。

先写测试时，你是站在"使用者"角度描述需求："顺子里有 2，应该判定非法"。这句话写下来，实现就必须满足它。

**每个测试只验证一件事，测试名要能当文档读。**

好用 vs 没用的测试名：

| 没用 | 有用 |
|---|---|
| `test1()` | `顺子不能包含 2` |
| `testParse()` | `三张不同点数的牌不能被识别成三张` |

后者失败时，你一眼知道哪里错了，不用去翻代码。

## 2. 六个台阶，顺序不能乱

```
阶段 1  牌与牌堆          Card / Deck                   0.5 天
   ↓    先有"牌"，才谈得上"牌型"
阶段 2  基础牌型 5 种      PatternType / CardPattern
                          / PatternParser               2 天
   ↓    先易后难，建立"按点数分组"的核心思路
阶段 3  顺子/连对/飞机     PatternParser 扩展             3 天  ← 最难
   ↓    复杂度最高的部分，单独一档
阶段 4  炸弹/王炸/四带二    PatternParser + Comparator    1.5 天
   ↓    有了 14 种牌型，才能比大小
阶段 5  枚举合法出牌      MoveGenerator                 2 天
   ↓    有了"判断一手牌"，才能"找出所有能出的牌"
阶段 6  回合与结算        GameState / TurnManager
                          / ScoreCalculator             2 天
```

**依赖关系是硬的**：阶段 3 依赖阶段 2 的分组思路，阶段 5 依赖阶段 2-4 全部做完。跳过任何一级，后面都会卡住。

## 3. 阶段 1：牌与牌堆（今天只做这个）

### 3.1 先想清楚 5 个问题，再动手

这些问题想不明白，写出来的代码一定会在阶段 3 崩。

**Q1：为什么点数用 3..17 的整数，不用 0..14 或 1..15？**

因为 3 对应 3，10 对应 10，读日志时 `rank=7` 你立刻知道是 7。用 0..14 的话，7 对应的是 10，每次看都要换算。

**Q2：2 为什么是 15，不是 2？**

斗地主里 2 只输给王。如果按扑克牌面值存 2，它比 3 还小，比大小全错。

但这里埋了一个陷阱：A=14、2=15 是连续的，可**顺子不能带 2**。所以阶段 3 判断顺子时，不能只看"连续"，还要加"点数 ≤ 14"。现在先记住。

**Q3：王的花色填什么？**

填 -1，不要填 0。因为 0 是黑桃，如果王用 0，`new Card(16, 0)` 和"黑桃某张牌"在代码里看起来一样，调试时会误判。用一个不可能出现的值标记"无花色"。

**Q4：`S3` 和 `H3` 相等吗？**

**不相等**。它们是两张实体牌，一手牌里可以同时存在。所以 `equals` 必须比较 rank **和** suit 两个字段。

如果你只按 rank 比较，`HashSet` 会把 S3 和 H3 当成同一张，去重时丢掉一张牌 —— 这种 bug 表现出来是"手牌少了一张"，极难定位。

**Q5：为什么需要一个 `id()` 字符串？**

因为 `{"cards":["S3","H3"]}` 要发给前端，`rank=3,suit=0` 这种对象没法直接塞进 JSON 让人读懂。同时牌谱回放、日志、测试断言都需要一个人类可读的短标识。

### 3.2 Card 要写什么

| 成员 | 类型 | 作用 |
|---|---|---|
| `rank` | int | 3..17，核心字段 |
| `suit` | int | 0..3，王为 -1 |
| `isJoker()` | boolean | 判断是不是王 |
| `id()` | String | 转成 `S3` / `H10` / `JOKER_S` |
| `of(String)` | 静态，返回 Card | `id()` 的反向操作 |
| `compareTo(Card)` | int | 排序用 |

**用 record 还是 class？**

用 record。它会自动生成 equals、hashCode、toString，正好满足 Q4 的要求（按全部字段比较）。手写 class 忘写 equals 是最常见的静默 bug。

代价：record 的字段是 final 的，不能改。牌本来也不该改，所以没损失。

**`id()` 的格式**

```
普通牌：花色字母 + 点数文本      S3  H10  CJ  DK  SA  S2
王：    JOKER_S / JOKER_B
```

注意 `H10` —— 点数文本有 1 位也有 2 位，反向解析时不能按固定位置切。先取第一个字符当花色，剩下**全部**当点数。

**`of()` 必须对非法输入抛异常**

`Card.of("X3")`、`Card.of("S1")`、`Card.of("S")` 都要抛 `IllegalArgumentException`，不能返回 null。

为什么？因为返回 null 会把这个错误推迟到几十行之后才炸，报错点离出错点很远。当场抛，堆栈直接指到问题所在。

### 3.3 Deck 要写什么

| 成员 | 作用 |
|---|---|
| `newDeck()` | 生成 54 张，**顺序固定** |
| `shuffled(Random)` | 洗牌，必须传入 Random |
| `deal(Random)` | 发牌，返回三家手牌 + 3 张底牌 |

**为什么 `newDeck()` 顺序必须固定？**

因为测试要能断言"第 0 张是黑桃3"。如果它内部随机，测试就没法写确定的断言。

顺序建议：从 3 到 2，每个点数按 黑桃→红桃→梅花→方块，最后加小王、大王。这样好推算，出 bug 时一眼能看出位置。

**为什么洗牌必须传 Random，不能内部 new？**

因为要能复现。`new Random(42)` 每次得到的洗牌结果一样，`new Random()` 每次不一样。

这直接决定了三件事能不能做：牌谱回放、复现线上 bug、写"发牌结果稳定"的测试。**这是设计决策，不是风格偏好。**

**`deal()` 返回什么**

两个选择：

| 方案 | 问题 |
|---|---|
| 返回 `List<List<Card>>` | 取牌要 `hands.get(1)`，索引写错编译器不管，运行时才炸 |
| 返回一个带字段名的结构（如 record Deal） | `deal.hand1()` 写错直接编译失败 |

选后者。让编译器帮你抓错，永远比让测试帮你抓错便宜。

### 3.4 验证清单（写完对着跑）

| # | 断言 | 为什么重要 |
|---|---|---|
| 1 | 一副牌 54 张 | 基础 |
| 2 | 放 HashSet 后还是 54 | 查重复，间接验证 equals |
| 3 | 大小王各 1 张 | 别漏了王 |
| 4 | 发牌 17/17/17/3 | 规则 |
| 5 | 四份合起来 54 张且无重复 | 查"同一张牌发给两个人" |
| 6 | 同 seed 两次发牌结果相同 | 验证可复现 |
| 7 | 54 张的 id 都能被 of 还原 | 验证编解码互逆 |
| 8 | 非法 id 抛异常 | 验证防御性 |

第 5 条最容易被忽略，但它防的是最伤的一类 bug：发牌时 `subList` 边界算错，某张牌发了两份，另一张丢了。这种局打到一半才会发现"牌对不上"。

### 3.5 阶段 1 的坑

| 坑 | 现象 | 原因 |
|---|---|---|
| 点数文本数组越界 | `ArrayIndexOutOfBounds` | 数组要能索引到 17，长度必须 ≥ 18，前面补空占位 |
| `H10` 解析错 | 花色被解析成 H，点数变成 1 | 不能用固定下标切，要点数取剩余全部 |
| 王被当成普通牌 | 王的花色变成 0 或 4 | 王要单独分支处理，不要走花色逻辑 |
| 去重后少牌 | HashSet 里只有 52 张 | equals 只比了 rank，没比 suit |
| 发牌张数对但内容错 | 17/17/17/3 都对，但某张重复 | subList 边界差一位 |

## 4. 阶段 2：五种基础牌型

### 4.1 核心洞察：只看点数有几张，花色完全不参与

这一条想通了，整个 Parser 都好写。

任何牌型，本质都是"**每个点数各几张**"的某种形状：

```
单张       → {某个点数: 1}
对子       → {某个点数: 2}
三张       → {某个点数: 3}
三带一     → {A: 3, B: 1}          两种点数，一个 3 一个 1
三带二     → {A: 3, B: 2}          两种点数，一个 3 一个 2
炸弹       → {某个点数: 4}
顺子       → {A:1, A+1:1, A+2:1, ...}   每个点数各 1，且点数连续
连对       → {A:2, A+1:2, A+2:2, ...}   每个点数各 2，且连续
飞机       → {A:3, A+1:3, ...}          每个点数各 3，且连续
```

所以 Parser 的固定第一步永远是：**把 List<Card> 转成 Map<点数, 张数>**，后面全部基于这张 Map 判断。

不这么做的人，会写出一堆"排序后取第 0 张、第 1 张比较"的代码。一旦遇到三带一（3 张在前还是 1 张在前不确定）就乱套。

### 4.2 PatternType 怎么写

建议**一次把 14 个枚举值全列出来**，即使这一阶段只实现 5 个。

理由：枚举值是稳定的，不会变。先列全，Parser 里没实现的直接抛"暂不支持"，你能清楚看到还差哪些。比一个个加更容易看到全局。

14 个值：单张、对子、三张、三带一、三带二、顺子、连对、飞机（纯）、飞机带单、飞机带对、四带二单、四带二对、炸弹、王炸。

### 4.3 CardPattern 是什么

它回答一个问题：**"这手牌是什么，多大"**。

需要的字段：

| 字段 | 作用 |
|---|---|
| type | 牌型 |
| mainRank | **主牌点数**，比大小只比它 |
| count | 张数，有些牌型靠张数区分（顺子长度不同不能比） |

**`mainRank` 概念要单独想清楚**，它是整个比大小机制的核心：

| 牌型 | 主牌是哪个 |
|---|---|
| 三带一 | 三张那个点数（带的牌不影响大小） |
| 飞机带单 | 三张序列里**最大**的那个点数 |
| 四带二 | 四张那个点数 |
| 顺子 | 最大的那个点数（或最小的，但要统一） |

**主牌取错了，比大小就全错，而且测试很难发现**（因为大多数情况下两个人都出同一种牌，比错了也看不出来）。所以阶段 4 写 Comparator 时，要专门为每种牌型写"主牌取值"的测试。

### 4.4 PatternParser 要写什么

| 方法 | 作用 |
|---|---|
| `parse(List<Card>)` | 返回 CardPattern；不合法返回空或抛异常 |
| 私有的各牌型识别方法 | 单张、对子、三张、三带一、三带二各一个 |

`parse` 的结构建议：

```
1. 空列表 → 非法
2. 按点数分组 → Map<点数, 张数>
3. 按"形状"依次尝试匹配：
   每种牌型有唯一确定的形状，匹配上就返回
4. 都不匹配 → 非法
```

**判断顺序有讲究**：先判少张数、形状唯一的（单/对/三/炸弹），再判带牌的（三带一/三带二）。因为 4 张同点既是"炸弹"也可能被误判成"三带一"（三张 + 一张同点？不成立，但逻辑写错就会）。**炸弹的判断必须在三带一之前。**

### 4.5 验证清单

正例和**反例**都要写，反例比正例更重要：

| 输入 | 期望 |
|---|---|
| 1 张 | 单张 |
| 2 张同点 | 对子 |
| 2 张不同点 | **非法** |
| 3 张同点 | 三张 |
| 3 张不同点 | **非法** |
| 4 张 = 3 同点 + 1 异点 | 三带一 |
| 4 张 = 2 同点 + 2 同点 | **非法**（不是三带一） |
| 4 张全同点 | **炸弹**，不是三带一 |
| 5 张 = 3 同点 + 2 同点 | 三带二 |
| 5 张 = 3 同点 + 2 异点 | **非法**（三带二必须带对子） |

只写正例的后果：实现里"3 张不同点判成三张"这种错，测试全绿，上线才炸。

### 4.6 阶段 2 的坑

- **先判炸弹再判三带一**，顺序反了 4 张同点会变三带一
- **三带二必须带对子**，带两张不同点数是非法
- **不要用"牌数 + 是否同点"硬凑**，一定走"分组 + 看形状"

## 5. 阶段 3：顺子、连对、飞机（最难，占 30% 时间）

### 5.1 先写文档，再写代码

动手前必须先建 `docs/牌型规则.md`，把下面这些逐条写成表格。**这份文档是唯一事实来源**，代码和它不一致时以文档为准、改代码。

理由：这一阶段的边界情况多到靠脑子记不住。写在纸上，你写 Parser 时是"对着清单实现"，不是"边写边想还有没有漏"。

### 5.2 三种牌型的算法骨架（文字版）

**顺子**

```
1. 张数 ≥ 5，否则不合法
2. 分组后每个点数必须恰好 1 张（有任何点数 2 张 → 不合法）
3. 所有点数 ≤ 14（即不含 2、不含王）
4. 按点数排序，从第二个开始逐个检查：当前 - 前一个 == 1
5. 全通过 → 顺子，主牌取最大点数
```

第 3 步是最容易漏的。漏了之后 `A,2,3,4,5` 会被判成合法顺子 —— 而斗地主里 2 不能进顺子。

**连对**

```
1. 张数 ≥ 6 且为偶数
2. 分组后每个点数必须恰好 2 张
3. 点数种类 ≥ 3
4. 所有点数 ≤ 14
5. 连续检查同顺子
```

**飞机（纯）**

```
1. 张数 ≥ 6 且能被 3 整除
2. 分组后每个点数必须恰好 3 张
3. 点数种类 ≥ 2
4. 所有点数 ≤ 14（这点要确认：飞机能不能含 2？按主流规则不能，写进你的规则文档里定死）
5. 连续检查同上
```

你先把"飞机能不能带 2"这条在文档里拍板，然后代码照着写。**规则有分歧的地方，自己定一个，写下来，全项目统一**。

### 5.3 飞机带单 / 飞机带对（真正的难点）

这是全项目最容易写错的地方。

**飞机带单**：n 组连续三张 + n 张单牌，总张数 4n。

思路：

```
1. 张数能被 4 整除，否则不合法
2. 从分组里找出"连续的三张组"（可能有多组，要找到最长的）
3. 设找到 m 组三张，则需要 m 张单牌
4. 剩下的牌（总数 - 3m）必须正好等于 m 张
5. 剩下的牌组成任意单张（可以是 2 和王，可以重复点数）
```

**这里有个歧义必须自己定**：如果手牌是 `333444555`，它可以是"3 组飞机的纯飞机"，也可以是"333444 + 555 当三张带两张？"—— 不成立，张数对不上。但如果是 `33344455` 呢？是"两组飞机 + 两张单"，还是别的？要在文档里定死优先级。

**飞机带对**：n 组三张 + n 个对子，总张数 5n。判断更麻烦，因为要给"三张"和"对子"分别配对。

**建议做法**：先只实现"飞机带单"，把"飞机带对"放到阶段 3 的最后。带对是最少用到的牌型，先做能用的。

### 5.4 验证清单（这一阶段测试量最大）

| # | 输入 | 期望 |
|---|---|---|
| 1 | 3,4,5,6,7 | 合法顺子，主牌 7 |
| 2 | 3,4,5,6 | **非法**（不足 5 张） |
| 3 | 10,J,Q,K,A | 合法，主牌 A（14） |
| 4 | J,Q,K,A,2 | **非法**（含 2） |
| 5 | 3,4,4,5,6 | **非法**（有重复点数） |
| 6 | 33,44,55 | 合法连对 |
| 7 | 33,44 | **非法**（不足 3 对） |
| 8 | 333,444 | 合法飞机，主牌 4 |
| 9 | 333,444,555 | 合法飞机，主牌 5 |
| 10 | 333,555 | **非法**（3 和 5 不连续） |
| 11 | 333,444 + 2 张单 | 飞机带单 |
| 12 | 333,444 + 2 个对 | 飞机带对 |
| 13 | 333,444 + 2 张王 | 飞机带单（王可以当单牌带） |

第 13 条是最容易漏的：带牌允许是王，但**主牌序列里不能有王**。两回事别混。

### 5.5 阶段 3 的坑

| 坑 | 后果 |
|---|---|
| 忘判 `≤ 14` | `J,Q,K,A,2` 被判成顺子 |
| 只判"张数够"，不判每个点数张数 | `3,3,4,5,6` 被判成顺子 |
| 飞机带单时把王也算进三张序列 | 王不可能有三张，逻辑会崩 |
| 连续检查用了原始列表而非去重后的点数列 | 顺序错乱时误判 |
| 主牌取成了最小值 | 比大小时小顺子压大顺子 |

## 6. 阶段 4：炸弹、王炸、四带二 + 比大小

### 6.1 剩余 4 种牌型

都很简单，但要接在阶段 3 之后，因为判断顺序上它们优先级最高：

| 牌型 | 判断 |
|---|---|
| 炸弹 | 4 张同点。**必须在三带一之前判** |
| 王炸 | 恰好 2 张，且是大小王各一张 |
| 四带二单 | 4 张同点 + 2 张任意单牌（总 6 张） |
| 四带二对 | 4 张同点 + 2 个对子（总 8 张） |

**四带二的坑**：那"二"不能是王炸拆开的两张王。如果你手上有大小王，不能拿它们当四带二的"二"。这条要写进规则文档。

### 6.2 比大小（PatternComparator）

规则只有三条，但要写成清晰的判断树：

```
1. 如果一手是王炸：
      是王炸 vs 任何非王炸 → 王炸赢
      王炸 vs 王炸 → 不能出（必须严格大于）
2. 如果一手是炸弹，另一手不是炸弹 → 炸弹赢
   两个都是炸弹 → 比点数
3. 其余情况：
      类型不同 → 不合法（不能比）
      类型相同 → 比 mainRank（严格大于才算能压）
      顺子/连对/飞机：张数还要相同才能比
```

**"严格大于"这一点要记住**：同点数不能压。这决定了 `MoveGenerator` 里筛选候选时的条件。

### 6.3 验证清单

| 场景 | 期望 |
|---|---|
| 炸弹 vs 单张 | 炸弹赢 |
| 王炸 vs 炸弹 | 王炸赢 |
| 炸弹 5 vs 炸弹 8 | 8 赢 |
| 对 3 vs 对 A | A 赢 |
| 对 A vs 对 A（不同花色） | **不能压** |
| 顺子 34567 vs 顺子 45678 | 后者赢 |
| 顺子 34567 vs 顺子 456789 | **不合法**（张数不同） |
| 三带一 vs 三带二 | **不合法** |

最后两条最容易漏，尤其是"张数不同的顺子不能比"。

## 7. 阶段 5：枚举所有合法出牌（MoveGenerator）

### 7.1 它的职责

输入：我的手牌 + 上家出的牌（可能为空，表示我首发）
输出：**所有我能出的牌的组合列表**

这是 AI 的原料。AI 的工作就是"从这些候选里挑一个"，而不是"凭空想一手牌"。这个设计直接决定了 AI 不会出非法牌。

### 7.2 两种场景

**首发（上家没牌）**：枚举手牌能组成的所有牌型。

**跟牌（上家有牌）**：只找
- 同类型、同张数、mainRank 更大的组合
- 所有炸弹
- 王炸（如果有）

### 7.3 实现思路（先写对的，不写快的）

最朴素的做法：

```
1. 手牌点数分组
2. 对每一种牌型，按规则从分组里"取牌"
   例如"找所有对子" = 遍历分组，每个张数 ≥2 的点数，取其中两张
3. 把找到的组合都 parse 一遍，能通过校验的加进结果
4. 跟牌时再按"能否压过上家"过滤
```

**不要一上来就优化性能。** 17 张手牌，组合数量在几千量级，Java 跑完只要几毫秒。先保证正确，等实测慢了再说 —— 而且大概率根本不需要优化。

### 7.4 验证清单

| 手牌 | 上家 | 期望 |
|---|---|---|
| S3 | 无 | 只有 1 种：单张 3 |
| S3 | S4 | **0 种**（压不住，只能 pass） |
| S3 H3 | 无 | 至少 3 种：单 3、单 3、对 3 |
| 有炸弹，上家出对 A | 对 A | 结果里**必须包含**炸弹 |
| S2 | S3 | 包含单 2 |

第 3 条要注意：`S3` 和 `H3` 是两个不同的单张出法，是否都要返回？从"能出什么"的角度是的，但从 AI 角度是重复的。**这里要做去重决策**，写进文档。

## 8. 阶段 6：回合与结算

### 8.1 三个类

| 类 | 职责 |
|---|---|
| `GameState` | 持有全部状态：三家手牌、地主是谁、当前轮到谁、上家出的牌、底牌、倍数 |
| `TurnManager` | 判断"现在轮到谁"、出牌后推进、判断三家都 pass 时是否要清空上一手 |
| `ScoreCalculator` | 算分 |

### 8.2 回合推进最容易错的地方

**三家连续 pass，上一手牌要清空，出牌权回到最后出牌的人。**

这条逻辑写错的表现：某个人 Pass 之后，下一个玩家还在跟"上上个玩家"的牌比，导致永远出不了牌或能出不该出的牌。

写 `TurnManager` 时，专门为这个场景写测试：

```
A 出牌 → B pass → C pass → 又轮到 A（A 可以随便出新的牌型）
```

### 8.3 倍数怎么算

```
最终倍数 = 叫分 × 2^炸弹数 × 春天倍数
春天：地主出完牌，两个农民一张没出 → ×2
反春：农民出完，地主只出了一手 → ×2
```

先把"炸弹数"在状态里累计，结算时一次性算。不要边打边乘，容易重复乘。

### 8.4 验证：脚本化一整局

写一个测试，用固定 seed 发牌，然后按预先写好的出牌序列把整局打完，断言最终分数。

这个测试的价值：它是**唯一能验证"整个流程串起来没错"的测试**。单元测试只验证零件，这个验证装配。

## 9. 每天怎么推进

推荐节奏（每天 1 小时左右）：

```
0-5 分钟     看昨天写的测试，跑一遍确认全绿
5-15 分钟    想今天的范围：只做一件事，写进测试名
15-45 分钟   红 → 绿 → 重构循环
45-55 分钟   补反例测试（这一步最容易被跳过，但价值最高）
55-60 分钟   跑全量测试，commit
```

**每次 commit 前必须全量测试绿。** 不允许"先提交，明天再修"——规则引擎一旦有红灯，后面所有工作都建在沙子上。

## 10. 卡住时的排查顺序

按这个顺序查，不要跳：

1. **测试报错还是编译报错？** 编译错先解决语法和 import
2. **断言失败的具体值是什么？** 期望 vs 实际，差在哪
3. **把输入打印出来**：手牌的 rank 列表、分组后的 Map
4. **手动推演一遍**：拿张纸，按你的算法走一遍这手牌
5. **算法和规则文档对不上？** 以文档为准

如果同一个问题改了 3 次还没好，停下来，把"输入、期望、实际、你的算法步骤"四样写下来。通常写到一半就发现错在哪了。
