## 1. 背景与目标

### 1.1 为什么要做

斗地主是规则封闭、状态机清晰的完全信息可视化博弈（对旁观者完全信息，对玩家不完全信息），非常适合作为**实时联网 + 规则引擎 + AI 决策**三合一的项目载体。它比 CRUD 项目多出三样东西：并发状态一致性、算法正确性、外部大模型集成。这三样恰好是简历里最难造假的部分。

### 1.2 项目目标

1. 实现一套**符合主流民间规则**的斗地主（含叫分、加倍、春天、炸弹翻倍、托管）。
2. 支持 **3 人实时联网**对局，断线可重连且状态完全一致。
3. 支持 **单人 vs 2 个 AI** 的人机对战，AI 不产生任何非法出牌。
4. 接入 **OpenAI 兼容协议的大模型 API**，让 AI 具备人格化台词与策略倾向，且**不因模型延迟或幻觉影响对局可用性**。

### 1.3 成功标准（验收即按此判定）

| 编号 | 指标              | 目标值                       |
| -- | --------------- | ------------------------- |
| S1 | 一局完整可玩          | 从发牌到结算全流程无阻塞              |
| S2 | 非法出牌率           | 0（服务端校验拦截，AI 与人类玩家同规则）    |
| S3 | 规则引擎单元测试覆盖      | ≥ 90%                     |
| S4 | AI 决策耗时（纯引擎）    | < 100 ms                  |
| S5 | 玩家感知出牌延迟（含 LLM） | < 1.5 s，超时自动降级            |
| S6 | 断网重连恢复          | 10 s 内重连，状态与服务端完全一致       |
| S7 | 并发对局            | 单机可承载 50 桌（150 个 WS 连接）不崩 |

## 2. 范围界定

### 2.1 V1 必做（MVP）

- 账号体系：注册 / 登录 / 昵称，Session 或 JWT 二选一（见 ADR-05）
- 匹配：随机匹配 3 人进房，支持邀请码进房
- 对局：叫分（1/2/3 分）→ 抢地主 → 出牌 → 结算
- 完整牌型：单、对、三、三带一、三带二、顺子、连对、飞机（不带/带单/带对）、四带二（两单/两对）、炸弹、王炸
- 倍数：底分 × 叫分 × 炸弹数 × 春天
- 人机对战：单人 + 2 AI，AI 人格 3 种
- 断线重连 + 托管（30 s 无操作自动代打）
- 战绩：历史对局列表、胜率统计、牌谱回放（只读）

### 2.2 明确不做（V1 划出边界，防止范围蔓延）

- 观战席、语音、好友系统、排行榜
- 癞子/天地癞子等变种玩法
- 移动端 App（响应式适配即可，不做原生）
- 纯离线可玩（浏览器断网仍能打）——**原因见 ADR-04**
- 充值、道具、皮肤商城

### 2.3 V2 展望（不在本次承诺内）

- 观战 + 弹幕
- 房间内自定义规则（炸弹限制、明牌加倍）
- AI 难度分级（基于蒙特卡洛搜索深度）
- 赛后 AI 复盘（异步调 LLM 出点评报告）

### 3.2 关键技术决策（ADR）

立项阶段必须先钉死这几条，否则开发中期会推倒重来。

#### ADR-01：规则引擎只实现一份，用 Java

**决策**：规则引擎（牌型、出牌枚举、状态机、结算）只在 Spring Boot 侧用 Java 实现，前端不重复实现。

**背景**：原计划里"联网 + 单机"容易让人以为单机模式要在浏览器里跑一套 TS 规则引擎。那样同一套规则会存在 Java 和 TS 两个版本，任何一处改动不同步，就会出现"客户端认为能出、服务端判非法"的玄学 bug，且这类 bug 极难定位。

**代价**：单机模式必须连得上后端。

**结论**：接受这个代价。V1 的"单机"定义为**人机对战（不需要匹配真人，随时开局）**，而非"断网可玩"。如果将来真需要离线，再考虑把引擎编译为 WASM，但这不在 V1 范围。

#### ADR-02：通信层用原生 WebSocket，不用 socket.io

**决策**：后端 Spring 的 `spring-boot-starter-websocket` + 原生 `WebSocketHandler`；前端用浏览器原生 `WebSocket` API 自封装（约 200 行）。

**背景**：socket.io 是 Node 生态的协议，Java 端只有 `netty-socketio` 这类社区实现，长期维护状态不佳，与 socket.io v4 客户端存在协议版本兼容风险。为了用 socket.io 而在 Spring Boot 上挂一个不活跃的中间件，收益为负。

**收益**：少一层协议、少一个依赖、Chrome DevTools 的 Network → WS 面板可直接逐帧查看收发内容，调试成本最低。

**替代方案**（如果后面发现需要 STOMP 的订阅模型）：`spring-boot-starter-websocket` 同时支持 STOMP，前端换 `@stomp/stompjs` 即可，改动集中在一层。

#### ADR-03：LLM 不直接生成牌，只做"动作选择 + 台词生成"

**决策**：由 Java 引擎枚举全部合法动作并编号，LLM 只输出 `actionId` 与台词，输出用 JSON Schema 强约束，且**返回后仍要过一遍引擎校验**。

**背景**：让模型直接生成牌的组合会同时踩中四个坑——牌型非法、手牌幻觉（给出手里没有的牌）、延迟 1–3 s、同局面结果不可复现导致无法测试。

**结论**：LLM 是"决策层的调味剂"，不是决策主干。超时或异常一律回落到引擎自算结果，玩家无感。

#### ADR-04：服务端权威，客户端永不接触他人手牌

**决策**：所有对局状态由服务端持有并计算；下发给某个玩家的快照中，其他玩家手牌只给**张数**，不给具体牌面。

**影响**：LLM 的 prompt 里同样不允许出现对手具体手牌，否则等于教 AI 作弊，且一旦前端抓包就能证实。

#### ADR-05：鉴权用 JWT，不用 Session

**决策**：`Access Token`（2 h，存内存）+ `Refresh Token`（7 d，HttpOnly Cookie）。

**背景**：WebSocket 握手阶段无法方便地带自定义 Header（浏览器限制），Session/Cookie 方案在跨域和 WS 场景下容易出问题。JWT 可以直接放在 WS 连接的 query 参数或首帧 `auth` 消息里，实现最干净。

#### ADR-06：接口文档用 springdoc + Swagger UI，不用 Knife4j

**决策**：`springdoc-openapi-starter-webmvc-ui` **3.0.3** + 其内置 Swagger UI。入口 `/swagger-ui.html`，OpenAPI JSON 在 `/v3/api-docs`。

**背景**：Knife4j 的最后一个版本是 **4.5.0（2024-01 之后停更）**，它依赖 `springdoc-openapi` **2.x**。而本项目是 Spring Boot **4.1.1**（Spring Framework 7），必须用 springdoc **3.x**——两者不在同一代，强行引入 Knife4j 会把 springdoc 沿依赖树降级到 2.x，结果是自动配置不生效、启动直接失败。

**代价**：失去 Knife4j 的三样东西——中文界面、离线文档导出（word/md）、调试增强面板。这三样对单人开发不是刚需。

**缓解**：业务代码里只写 OpenAPI 3 标准注解（`@Tag` / `@Operation` / `@Schema` / `@Parameter`），**不写任何 Knife4j 私有注解**。哪天 Knife4j 适配了 Boot 4，只需换一个 starter + 一行配置，接口代码零改动。

**结论**：接受。文档的价值在契约本身，不在 UI 皮肤。

#### ADR-07：Redis 用 Docker 起，不装宿主机版

**决策**：Redis 一律跑容器 `redis:7-alpine`，本地与生产同一镜像。启动参数统一为 `--appendonly yes --maxmemory 256mb --maxmemory-policy allkeys-lru`。

**背景**：Windows 上没有官方 Redis，只有第三方移植版，且停留在 **5.0.14.1（2022 年）**。用它开发会踩两类坑：一是与线上 7.x 的版本差 6 个大版本，`ACL`、`Redis Stack`、部分命令直接没有；二是查到的排错资料几乎都是 Linux/7.x 语境，对不上号。

**代价**：本地开发必须让 Docker Desktop 常驻，多占约 1–2 GB 内存。

**结论**：接受。**环境一致性**的收益远大于这点开销，而且 `deploy/docker-compose.yml` 本来就要求容器化，本地提前对齐，M5 部署时不会突然冒出一堆环境问题。

**对原技术清单的 4 处修正（重要）：**

1. **Zustand → Pinia**。Zustand 是 React 专用，Vue 下没有意义，直接用 Pinia。

## 4. 数据模型

### 4.1 MySQL 表结构

> **事实来源**：可执行的完整 DDL 在 `backend/src/main/resources/db/schema.sql`——幂等（全部 `IF NOT EXISTS`），  
> 本地手动执行与容器首次启动导入共用同一份。本节为设计稿，若有出入**以 `schema.sql` 为准**。
>
> 相比 v1.0 设计稿，实际建表补了四处：`user.deleted` 与 `ai_persona.deleted`（软删除，配合  
> MyBatis-Plus 的 `logic-delete-field`）、`user.updated_at`、以及 `game_record.landlord_id` 的索引。  
> 另外 `ai_persona` 内置了 3 条种子数据，M2 做 AI 时可直接用。

```sql
-- 用户
CREATE TABLE `user` (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  username      VARCHAR(32)  NOT NULL UNIQUE,
  password_hash VARCHAR(100) NOT NULL,
  nickname      VARCHAR(32)  NOT NULL,
  avatar        VARCHAR(255) DEFAULT NULL,
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 对局记录（一条 = 一局）
CREATE TABLE game_record (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  room_id       VARCHAR(32)  NOT NULL,
  landlord_id   BIGINT       NOT NULL,
  winner_side   TINYINT      NOT NULL COMMENT '1=地主胜 2=农民胜',
  base_score    INT          NOT NULL,
  multiplier    INT          NOT NULL COMMENT '叫分×炸弹×春天',
  bomb_count    INT          NOT NULL DEFAULT 0,
  players_json  JSON         NOT NULL COMMENT '座位、用户、身份、得分',
  replay_json   MEDIUMTEXT   NOT NULL COMMENT '逐手牌谱，用于回放',
  started_at    DATETIME     NOT NULL,
  ended_at      DATETIME     NOT NULL,
  INDEX idx_room (room_id),
  INDEX idx_started (started_at)
);

-- 战绩统计（对局结束时增量更新）
CREATE TABLE player_stat (
  user_id         BIGINT PRIMARY KEY,
  total_games     INT NOT NULL DEFAULT 0,
  win_games       INT NOT NULL DEFAULT 0,
  landlord_games  INT NOT NULL DEFAULT 0,
  landlord_wins   INT NOT NULL DEFAULT 0,
  max_streak      INT NOT NULL DEFAULT 0
);

-- AI 人格配置（可在后台调，不用改代码）
CREATE TABLE ai_persona (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(32) NOT NULL,
  avatar      VARCHAR(255) DEFAULT NULL,
  style       VARCHAR(32) NOT NULL COMMENT 'steady/aggressive/talkative',
  prompt_hint TEXT NOT NULL COMMENT '注入 system prompt 的性格描述',
  temperature DECIMAL(2,1) NOT NULL DEFAULT 0.8
);
```


### 4.2 Redis Key 设计

| Key                     | 类型            | TTL  | 用途                        |
| ----------------------- | ------------- | ---- | ------------------------- |
| `room:{roomId}`         | Hash          | 2 h  | 房间全量状态（座位、身份、手牌、当前回合、seq） |
| `room:{roomId}:seq`     | String(INCR)  | 2 h  | 下行消息单调序号                  |
| `online:{userId}`       | String        | 60 s | 在线心跳，WS 收到 pong 即续期       |
| `match:queue`           | ZSet          | —    | 匹配队列，score = 入队时间戳        |
| `llm:cache:{stateHash}` | String        | 1 h  | 同一局面的决策缓存，省 token         |
| `lock:room:{roomId}`    | String(SETNX) | 5 s  | 防止并发出牌请求进入同一房间            |

**关键点**：房间状态放 Redis 而非纯内存，是为了将来后端多实例时能横向扩展。V1 单实例也照此设计，改造成本为零。

### 5.2 WebSocket 事件（`/ws/game`）

统一信封：`{ "type": "...", "seq": 12, "ts": 1730..., "data": {...} }`

**上行（Client → Server）**

| type    | data                   | 说明             |
| ------- | ---------------------- | -------------- |
| `auth`  | `{token}`              | 连接后首帧，鉴权       |
| `ready` | `{}`                   | 准备             |
| `bid`   | `{score: 0\|1\|2\|3}`  | 叫分，0 = 不叫      |
| `play`  | `{cards: ["S3","H3"]}` | 出牌             |
| `pass`  | `{}`                   | 要不起            |
| `chat`  | `{text}`               | 快捷语            |
| `ping`  | `{}`                   | 心跳，服务端回 `pong` |

**下行（Server → Client）**

| type         | data                                 | 说明                 |
| ------------ | ------------------------------------ | ------------------ |
| `auth_ok`    | `{userId}`                           | 鉴权通过               |
| `room_state` | 全量快照                                 | **加入/重连时必发**，含 seq |
| `deal`       | `{hand: [...], bottom: 3}`           | 发牌（仅自己的手牌）         |
| `bid_turn`   | `{seat, deadline}`                   | 轮到谁叫分              |
| `landlord`   | `{seat, bottom: [...], multiplier}`  | 地主确定，亮底牌           |
| `play_turn`  | `{seat, deadline}`                   | 轮到谁出牌              |
| `played`     | `{seat, cards, patternName, remain}` | 某家出牌               |
| `passed`     | `{seat}`                             | 某家不要               |
| `game_over`  | `{winnerSide, multiplier, scores}`   | 结算                 |
| `error`      | `{code, msg}`                        | 业务错误（如"牌型不合法"）     |

**三条铁律**：

1. **所有下行都带 `seq`**，客户端按 seq 丢弃重复 / 乱序消息。
2. **重连只走全量快照**（`room_state`），不做增量重放。增量重放是状态不一致的头号来源。
3. **`deadline` 是服务端绝对时间戳**，前端据此渲染倒计时，不使用前端本地计时器判定超时。

## 6. AI 出牌方案

### 6.1 分层设计（对应决策链路）

```
GameState
   ↓
MoveGenerator          枚举全部合法出牌（含"要不起"）
   ↓
Evaluator              对每个候选打分：拆牌代价、剩余牌力、队友配合、是否留炸弹
   ↓
MonteCarlo（V1.5）     按已出牌推断对手手牌分布，采样 N 次模拟
   ↓
LlmAdvisor（V1 末）   从候选里挑一个 + 生成台词，超时即跳过
   ↓
RuleValidator          最终校验，非法则回落 Evaluator 最优解
   ↓
出牌事件
```

### 6.2 三档 AI 难度（用同一套引擎，只调参）

| 档位 | 策略                                 | 用于     |
| -- | ---------------------------------- | ------ |
| 简单 | 只按 Evaluator 打分，不搜索，不调 LLM         | 新手教学关  |
| 普通 | Evaluator + 蒙特卡洛 100 次采样           | 默认人机对战 |
| 困难 | 蒙特卡洛 500 次 + LLM 参与关键决策（残局 / 炸弹时机） | 挑战模式   |

### 6.3 LLM 接入规范

```java
// 请求体（OpenAI 兼容 /v1/chat/completions）
{
  "model": "deepseek-chat",
  "messages": [
    { "role": "system", "content": "你在打斗地主，风格：{persona.prompt_hint}。只能从候选动作中选一个。" },
    { "role": "user", "content": "{局面摘要}\n候选动作：\n1. 对8\n2. 对A\n3. 炸弹5555\n请只返回 JSON。" }
  ],
  "response_format": { "type": "json_schema", "json_schema": { ... } },
  "temperature": 0.7,
  "max_tokens": 150
}
// 期望响应
{ "actionId": 2, "say": "这张你压不住吧" }
```


**工程约束（全部为硬性要求）：**

| 约束 | 做法 |
|---|---|
| 超时 | 连接 800 ms / 读取 1200 ms，超时抛异常走降级 |
| 降级 | 捕获一切异常（超时、429、格式错、actionId 越界），回落 Evaluator 结果 |
| 缓存 | key = `sha256(手牌+上家出牌+所有人剩余张数)`，命中直接返回 |
| 频率 | 仅"普通/困难"档调用；且同一局内每次决策都调会导致成本和延迟双爆，建议关键决策才调 |
| 脱敏 | prompt 内**绝不含**对手具体手牌 |
| 可观测 | 每次调用记录：耗时、是否降级、token 数、actionId、是否被校验打回 |

**必须是异步的**：LLM 调用放在独立线程池（核心 4 / 队列 32 / 拒绝策略 CallerRuns→改为降级），绝不阻塞 WS 的 IO 线程。

## 7. 规则引擎设计要点

这是全项目技术含量最高的部分，单独立章。

### 7.1 牌的表示

```java
// 用 int 编码，便于排序和位运算
// 3..10 = 3..10, J=11, Q=12, K=13, A=14, 2=15, 小王=16, 大王=17
// 花色：0=♠ 1=♥ 2=♣ 3=♦
record Card(int rank, int suit) {}
// 唯一字符串标识：S3 / H10 / C_2 / JOKER_S / JOKER_B
```

### 7.2 牌型枚举（共 14 类）

| 牌型 | 张数 | 说明 |
|---|---|---|
| 单张 | 1 | |
| 对子 | 2 | |
| 三张 | 3 | |
| 三带一 | 4 | |
| 三带二 | 5 | 带对子 |
| 顺子 | ≥5 | 连续单张，不含 2 和王 |
| 连对 | ≥6 | 连续对子（≥3 对），不含 2 和王 |
| 飞机（纯） | ≥6 | 连续三张（≥2 组） |
| 飞机带单 | 4n | n 组三张 + n 张单 |
| 飞机带对 | 5n | n 组三张 + n 个对 |
| 四带二（单） | 6 | 四张 + 2 张单 |
| 四带二（对） | 8 | 四张 + 2 个对 |
| 炸弹 | 4 | |
| 王炸 | 2 | 大小王 |

**边界 case 清单**（写测试时逐条覆盖，这些是血泪）：
- 顺子 / 连对 / 飞机**不能含 2 和王**
- 四带二里的"二"可以是对子也可以是两单，但**不能是王炸拆开**
- 飞机带单时，带的单**可以是 2 和王**
- 三带二带的对**不能是王炸**
- 炸弹可以压任何非炸弹牌型，王炸压一切
- 同牌型比大小只比**主牌**（三带一比三张，飞机比三张部分）

### 7.3 出牌枚举算法

```
generateMoves(hand, lastPattern):
  if lastPattern == null:
     → 枚举 hand 能组成的全部牌型（按牌型分类生成）
  else:
     → 只生成"同类型且更大"的组合 + 所有炸弹 + 王炸
  附加：pass 永远是合法选项（除非自己首发）
```

手牌拆分（`HandSplitter`）用**贪心 + 回溯**：先拆炸弹/王炸（保留），再拆顺子（最长优先），再拆连对，最后三张/对子/单张。回溯层数限制 3 层防止爆炸。

### 7.4 状态机

```
WAITING → BIDDING → PLAYING → SETTLING → CLOSED
            ↓ 三家都不叫
          REDEAL（重新发牌）
```

每个状态转移必须是**幂等**的，且转移前校验当前状态，防止重复出牌请求导致的越轨。
